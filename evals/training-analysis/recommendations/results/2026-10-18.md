# Sol / Luna recommendation eval — 18 October 2026

## Scope and reproducibility

Offline interpretation of five synthetic scenarios using production recommendation
helpers, frozen Xert calculations and copied skill instructions. No live calendar,
Garmin, Xert acquisition, full CLI orchestration or real training decision was tested.
Models: `gpt-6.1-sol` and `gpt-6-luna`, medium effort, fresh ephemeral read-only
sessions. This is a small, unblinded development evaluation, not a reliability
benchmark or proof of improvement over the original skill.

Full answers, execution transcripts, input snapshots and SHA-256 manifests are
retained locally in `outputs/training-recommendation-eval/2026-10-18/` (Git ignored).
`initial-inputs/` is a preserved copy of the original temporary input package;
commands in `runs/manifest.json` retain the original absolute paths. `final-inputs/`
and `final-runs/` use the final instruction revision. The adjacent JSON report
records answer hashes and reviewer findings. Execution success is not semantic pass.

## Initial sweep: five cases per model

Both models distinguished missing direct recovery signals from confirmed readiness
and avoided subtracting completed XSS twice. Both downgraded the adverse-response
case. Significant communication/execution omissions remained:

| Case | Sol | Luna |
|---|---|---|
| Missing recovery | Provisional VT2, correct timeline and before-third check; omitted explicit sync request and separate aerobic-purpose explanation. | Also omitted sync request and separate aerobic-purpose explanation; otherwise sensible provisional plan. |
| Normal recovery | Exact timeline and countable fuel; aerobic extension explained mostly as accounting, not its training purpose. | Put cooldown in the quality part before filler, then said filler had an easy start/finish. No countable fuel allocation or explicit queued-quality consequence. |
| Adverse response | Explicit rest override, conditional short easy ride, VT2 stays queued. Noted conflict with old packet rule allowing only new evidence. | Explicit short easy override; did not explicitly preserve queued VT2 and did not explicitly distinguish the override from historical-load subtraction. |
| Later full window | Correct noon start, full dose, setup and cleanup times. Aerobic-purpose explanation remained thin. | Noon start retained, but no exact cleanup time; alternative used 205-minute route reference instead of prescribed 245-minute duration. Incorrectly named High as limiting capacity. |
| Remaining after quality | Correct 260 Low remaining, 4:05:29 timeline, no repeated quality. | Correct remaining dose and separate VT1, with rounded duration; used morning weather to justify an afternoon choice. |

Representative evidence:

- Sol missing: “ikke bekreftet fysiologisk beredskap”
  and a checkpoint before the third repetition; no sync action in the answer.
- Luna normal: “avslutt med 3 min rolig nedkjøring” inside the quality portion,
  followed by “VT1-del: 98,3 min ... med lett start og avslutning”. This conflicts
  with the canonical final cooldown after continuous VT1.
- Luna later: “Ta den beregnede **205 min VT1-runden**”; the packet prescribes
  245:29 with a 205:12 route reference, so this changes the alternative's dose.
- Sol adverse: “Disse opplysningene finnes allerede i pakken”; the evidence was
  available, but the old override rule incorrectly demanded new information.

## Changes prompted by the sweep

The final contract now explicitly checks segment order and total/end time against
`executable_now.timeline`, distinguishes route reference time from prescribed
session duration, requires a separate purpose for aerobic extension, and explicitly
requests device sync/body feel when missing. The packet and skill allow an override
from narrative evidence not accounted for by the model decision, even if already
present in the packet. No readiness policy was automatically tightened just because
direct observations are absent.

## Final targeted sweep: three cases per model

All six executions completed with unchanged input hashes. Sol satisfied all
case-specific requirements in missing recovery, normal recovery and later full
window. It now explicitly requested sync, explained the aerobic addition and used
exact execution order, duration and calendar arithmetic.

Luna corrected the cooldown order in all three, but **none passed the full case
rubric**:

- Missing recovery: “synk enheten” is now explicit, but the specific checkpoint
  remains “før drag nummer to”. It does not require a check after the historically
  problematic late-second interval before continuing to the third.
- Normal recovery: correct segment order, but only approximate total time;
  no complete fuel allocation, concrete alternative or numeric capacity maximum.
- Later window: correct main timeline, but outdoor prescription becomes
  “205 min 29 sek”, instead of 245 min 29 sec. The approximately 40-minute
  dose shortfall is not declared. This is material, not just rounding.

There were **16 model executions total** (10 initial + 6 targeted). The two
unchanged scenarios were not rerun against the final instructions. Results justify
keeping the suite and the explicit evidence/timeline contract; they do not justify
calling Luna consistently correct or attributing differences to the model family
from this sample. Further work should prioritize validation of structured final
prescriptions, especially alternative durations, rather than more prose rules.

A fixture limitation: `fresh_at` is explicit in every case, but the next workout
start is explicitly confirmed in scenario prose only for the later-window and
remaining-after-quality cases. Do not score a cautious distinction between that
model horizon and an actual appointment as an error in the other cases.

No source fetches or writes were observed. Final Luna missing-recovery read the
original repository SKILL.md outside its allowed case folder. Its content matches
the frozen snapshot, but this is a protocol violation: that sample is not a clean
isolated comparison. The other recorded commands stayed within the case folders.
Final inputs were under the repository's ignored outputs folder, unlike initial
inputs under /private/tmp; inherited repository context is a potential confound.
Prepare future runs outside the repository and copy them into outputs only after
completion. Full command lists are in the JSON review. The rubric was not
provided to the evaluated models.

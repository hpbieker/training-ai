# Xert evaluation — 17 October 2026

All 155 local Xert tests passed in an isolated Python 3.14 environment with
MCP 1.30.0 and AnyIO 4.15.1, including schema and stdio handshake tests. No
production-code fix was necessary; the previous errors were absent dependencies.

Eight fresh model sessions used four synthetic cases, once each on gpt-6-sol
and gpt-6-luna at medium effort. Each package held the current skill, scenario
data and relevant actual MCP schemas, without review criteria. Models proposed
calls; there was no live Xert connection. Raw answers and commands are archived
under `outputs/xert-skill-eval/2026-10-17/`; all input hashes remained unchanged.

| Case | Sol | Luna |
| --- | --- | --- |
| Remaining dose after completed activity | Pass: 80 Low XSS, no second subtraction | Pass: 80 Low XSS, no second subtraction |
| Capacity versus advised dose | Pass: 180 is capacity, not a dose target | Pass: 180 is capacity, not a dose target |
| Positive Low recovery time | Pass: contextual assessment, no automatic ban | Pass: contextual assessment, no automatic ban |
| Multiple planned workouts | Correct aggregation and tool choice; timestamp anchor needs correction | Correct aggregation and tool choice; timestamp anchor needs correction |

Both models correctly aggregated the same-day Planner events into one impulse
of 100 Low, 3 High and 0.5 Peak XSS at the last event time. Neither invented a
`simulate_calendar_sequence` MCP tool, passed unsupported CLI flags, or fabricated
numerical Training Load/signature results.

However, both proposed `workout_after_hours=33` from the fixture's wall-clock
`now`. The service measures that offset from the freshly fetched Xert
`at_state.start_date`, whose value was unavailable in the fixture. The proposed
number is only valid if those timestamps coincide, which neither answer made
conditional. This is an additional correctness issue discovered during review,
not a failure of the original explicit tool-name checks. Six answers are clean
passes; two need that qualification or corrected source anchoring.

Recommended follow-up: make the source-state timestamp explicit in the tool
contract and skill examples. Consider an absolute workout timestamp to avoid
having callers compute an offset against a state fetched again inside the tool.
Do not change model arithmetic based solely on this interpretation test.

Luna often read most references despite the narrow routing guidance. Correct
answers do not establish that the shorter entrypoint reduces context usage.

This is a small, manual, non-blinded evaluation with one answer per model/case,
not a controlled comparison with the old skill and not live integration testing.
The [per-answer review](2026-10-17.json) retains full answers and findings.
